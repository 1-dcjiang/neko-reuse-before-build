# 四种结论的交付形态

示例都是“用户提出一个功能请求”的场景。照最接近的一个写，别自创格式。四个完整示例都能直接交给 `rbb_check` 做结构检查。

> **示例里的仓库名、star 数、日期、issue 号全部是虚构的占位，只用来演示格式。** 真实交付时禁止照抄或引用这些数字——按 `SKILL.md` 规则 1，任何未实时核实的仓库事实都必须标“未核实”。

## 例 1 · Join（最理想）

> 用户：“帮我写一个把长视频自动切成短视频的工具。”

```markdown
## 找到了什么
| 仓库 | ★ / 最近提交 | 许可 | 与需求的差距 |
|---|---|---|---|
| owner/autoclip | 4200 / 2026-10-01 | MIT | 已有切片与静音检测，缺字幕驱动的高光挑选 |
| other/clipbot | 890 / 2025-12-01 | GPL-3.0 | 全功能但闭源商用受限，且半年无提交 |

## 为什么选它
issue #212 已确认这个需求且维护者明确欢迎 PR；接口 `ClipPlanner` 已预留，改动可控制在 2 个文件。

## 我要加的东西（Issue / PR 计划）
- 新增 `src/planner/transcript_highlighter.py`，复用现有 `ClipPlan` 数据结构
- 测试：`tests/test_transcript_highlighter.py`（单高光、多高光、字幕缺失回退）
- 可改性：绿（内核清晰、接口稳定且有测试）；推送 `feat/transcript-highlights`，先 issue 后 PR
- 文档补 Options 与 CHANGELOG，预计 diff 约 180 行

## 备选与风险
- 若维护者要求换接口：改为插件式 `planner` 注册，不碰核心
- other/clipbot 的 GPL-3.0 不适合闭源分发，不用

结论：Join。
```

## 例 2 · Extend（核心不收，但仍进生态）

> 用户：“给我做一个 VS Code 里自动整理 import 顺序的插件。”

```markdown
## 找到了什么
| 仓库 | ★ / 最近提交 | 许可 | 与需求的差距 |
|---|---|---|---|
| owner/import-tools | 800 / 2026-09-15 | MIT | 官方插件接口稳定，但缺按项目分组的排序器 |

## 为什么选它
上游不接受新的核心排序策略，但提供公开的插件注册接口；做官方扩展即可复用生态，不做第 N 个同款插件。

## 我要加什么
- 新增官方扩展 `grouped-imports`，注册到上游公开 hook，不修改核心
- 可改性：黄（接口稳定、内部实现混乱）；通过 `src/adapters/import_tools.py` 薄适配层调用，并补契约测试
- 推送 `feat/grouped-imports-extension`，先发 issue 确认扩展形态，再提 PR

## 备选与风险
- 若扩展接口不足：改为独立官方插件，注明 derived from，保留 LICENSE 与版权声明
- 原插件维护者长期不回应时，再评估 Fork；不得把 monkey-patch 当交付

结论：Extend。
```

## 例 3 · Fork（维护者失联）

> 用户：“这个库不支持 Python 3.13，能改一下吗？”

```markdown
## 找到了什么
| 仓库 | ★ / 最近提交 | 许可 | 与需求的差距 |
|---|---|---|---|
| owner/libx | 1800 / 2024-06-01 | MIT | issue 有 30+ 条 Python 3.13 兼容请求，维护者失联 |

## 为什么选它
许可允许分叉，需求方向仍一致；先做最小兼容修复并回提 PR，不借兼容性修复另造一套 API。

## 我要加的东西
- 新建 `owner/libx-modern`，首行注明上游链接与 Fork 原因，添加 `upstream` remote 并保持同步
- 可改性：红（全局状态、循环依赖且无测试）；只做 Python 3.13 最小修复，不在此 Fork 上叠加无关功能
- 推送 `fix/python-313`，带兼容性测试、README 维护责任说明与 CHANGELOG，并向上游回提一次 PR

## 备选与风险
- 上游合并后立即切回上游并归档 Fork
- 长期无人合并时，这个 Fork 由用户自己维护，不假装是官方项目

结论：Fork。
```

## 例 4 · Build（例外，必须写明原因）

> 用户：“我们公司内部要一个把工单系统数据同步到内网数据库的 Daemon，代码不能外传。”

```markdown
不可复用原因：私有/闭源要求（公司内部资产，代码不得上传）；候选 owner/ticketsync（MIT）功能匹配 80%，但接入方要求源码不外流，因此不 Fork、不提 PR，只在本机实现。

## 找到了什么
| 仓库 | ★ / 最近提交 | 许可 | 与需求的差距 |
|---|---|---|---|
| owner/ticketsync | 600 / 2026-08-20 | MIT | 功能匹配，但公开贡献与源码不得外流的硬要求冲突 |

## 为什么选它
没有能满足私有部署且代码不上传的公开仓库；候选的可改性不能覆盖用户的保密要求。

## 我要加的东西
- 在本机实现私有 Daemon，以依赖形式引入 MIT/Apache 组件，不复制受限代码
- 可改性：红（候选核心为上帝文件且无测试）；即使不考虑保密要求，也不能 Join 红档候选
- 分离“可私有实现”与“必须依赖开源”的边界，先做本地测试，不向远端推送

## 备选与风险
- 若用户允许公开：改走上游贡献并先确认 issue/PR 正文
- 记录每个依赖的许可与数据出境边界，避免把私有工单数据写入公开 issue

结论：Build。
```
